# ConceptTree 优化方案讨论

> 日期：2026-05-17

---

## 一、性能优化（快速解决方案）

**内容加载慢的根因：** 目前是两步串行调用：`parse_goal`（4096 tokens）→ `generate_graph`（4096 tokens），两次完整 LLM 调用。

### 优化对照表

| 问题 | 当前状态 | 优化方案 |
|------|---------|---------|
| parse_goal 太慢 | temperature=0.7, max_tokens=4096 | 换小模型（Haiku/GPT-mini），max_tokens 降到 800，这个任务很简单 |
| generate_graph 首字延迟高 | 完整生成后才 SSE | 改成 LLM 真流式 token-level streaming，边生成边解析节点（需要 JSON streaming parser） |
| 两步串行 | parse → wait → generate | parse 完成后立刻触发 generate，前端无需等待用户确认 interpretation 直接并发 |
| 无缓存 | 每次调用 LLM | 加 Prompt Caching（Claude API 的 cache_control 或 Redis key on hash(input)） |

**最简单立竿见影的：** parse_goal 降 max_tokens 到 800 + 换更快的模型。

> 待确认：当前 configs 里没有写 `model` 字段，走的是 client 默认值，需要确认是什么模型。

## 二、动态节点数量 + 核心内容数量（Multi-Agent 头脑风暴）

### 当前问题

`generate_graph.json` 虽然给了节点数量范围（explore: 5-7、apply: 7-10、master: 10-15），但 `what` 和 `mastery` 列表是 LLM 照着 output_format 模板写的——模板是 2-3 个，它就生成 2-3 个。

---

### 设想一：直接改 Prompt 让 LLM 自决数量

最简单的改法，不改架构，在 prompt rules 里去掉固定数量：

```
"Node count: decide based on topic complexity. A simple skill needs 5 nodes, a deep domain needs 20+. Do not pad or truncate."
"what items: list ALL distinct topics the learner must understand for this node. Not a fixed count."
```

**优点：** 改动小，快速上线  
**缺点：** LLM 在一次大输出里质量不稳定；节点越多越容易出错；单次 prompt 同时规划整个图 + 生成每个节点内容，注意力被稀释，内容浅的根本原因没有解决。

---

### 设想二：Multi-Agent 两阶段管道（推荐）

#### Phase 1 — Curriculum Architect Agent（快，输出骨架）

- **输入：** 学习目标 + 用户背景 + learning_purpose
- **输出：** 图的骨架结构，包含：
  - 节点名称列表（LLM 自由决定数量）
  - 每个节点的 phase、前置依赖关系
  - 每个节点预估的 what 项数量
- **模型：** 可以用较小的模型，速度快

#### Phase 2 — Content Generator Agent（每节点独立，可并发）

- **输入：** 单个节点名称 + 学习目标 + 阶段上下文
- **输出：** 该节点的完整内容（why、what 列表、mastery、prompt）
- **运行方式：** 所有节点**并行调用**，总时间接近"最慢节点时间"

```
用户输入
   │
   ▼
Phase 1: Curriculum Architect Agent
   │  输出图骨架（节点名称、依赖、预估深度）
   ▼
Phase 2: Content Generator Agent × N（并发）
   │  每个节点独立生成详细内容
   ▼
SSE 流式返回给前端
```

#### 优势分析

| 维度 | 当前单 Agent | Multi-Agent 两阶段 |
|------|-------------|-------------------|
| 节点数量 | 固定范围 prompt 约束 | Phase 1 自由决定，无硬性约束 |
| 内容深度 | 模型注意力分散（要同时规划 N 个节点） | Phase 2 全力关注单个节点 |
| 速度 | 串行生成所有节点 | Phase 2 并发，总时间大幅缩短 |
| 可维护性 | 单一大 prompt，改动影响全局 | 两个 prompt 职责分离，可独立优化 |
| 错误恢复 | 一个节点出错影响全部 | 单节点失败可独立重试 |

#### 关键设计问题（待讨论）

1. **Phase 2 最大并发数**：限制 `asyncio.gather` 最多 8 个并发，避免 API 限流
2. **SSE 流式策略**：Phase 1 完成后先发 `meta`（节点骨架），Phase 2 每完成一个节点发一个 `node` 事件
3. **节点数量上限**：如果 Phase 1 输出 25+ 节点，是否给用户一个精简选项？
4. **失败处理**：Phase 2 某个节点生成失败，是用占位内容还是重试？

## 三、Prompt 自动迭代 Agent（可复用 AI Infra）

本质是 **DSPy 的核心思想** 的轻量级自实现，作为独立的工具链。

### 整体架构

```
Benchmark 数据集
       │
       ▼
Evaluator Agent（强模型打分）
       │
       ▼
Optimizer Agent（生成改进 Prompt）
       │
       ▼
候选 Prompt 版本 → A/B 测试 → 版本控制
       │
       ▼
部署到 configs/*.json
```

### 各组件说明

#### 1. Benchmark 数据集

收集"标准输入 → 期望输出"样例，例如：
- 10 个不同复杂度的学习目标
- 对应的理想节点图结构（由专家人工标注或高质量模型生成）

#### 2. Evaluator Agent

用强模型（Claude Opus / GPT-4o）按维度打分：

| 评估维度 | 说明 |
|---------|------|
| 节点覆盖率 | 关键概念有没有遗漏 |
| 依赖关系逻辑性 | 前置关系是否合理 |
| 内容深度 | what 列表质量和详细程度 |
| 学习目标对齐 | 图是否真正服务于用户目标 |
| 结构合理性 | phase 分组、节点数量是否适当 |

#### 3. Optimizer Agent

- **输入：** 当前 prompt + 失败样例 + 各维度分数 + 失败原因分析
- **输出：** 改进版 prompt + 改进原因说明
- **策略：** 每次只改一个维度（避免改动过多无法归因）

#### 4. 版本管理

```json
{
  "version": "v1.3",
  "timestamp": "2026-05-17",
  "prompt_hash": "abc123",
  "scores": {
    "coverage": 0.82,
    "logic": 0.91,
    "depth": 0.74,
    "alignment": 0.88
  },
  "change_log": "增加了对 what 列表深度的约束，修复了浅层内容问题"
}
```

### 实现建议

- **做成独立 CLI 工具**，不混入主应用：`python optimize_prompt.py --target generate_graph --runs 5`
- 本地跑"优化循环"，确认新 prompt 分数更高后，手动部署到 `configs/*.json`
- 可以复用到所有 `configs/` 下的 prompt 文件

## 优先级建议

| 优先级 | 任务 | 预期收益 |
|--------|------|---------|
| 🔴 P0 | parse_goal 降 max_tokens + 换快模型 | 立竿见影，加载时间减半 |
| 🟠 P1 | Multi-Agent 两阶段管道设计与实现 | 内容质量大幅提升 |
| 🟡 P2 | Prompt 自动迭代 Agent（独立 infra） | 长期持续优化能力 |
